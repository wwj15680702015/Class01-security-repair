## 三、漏洞详情

### V-01 任意文件上传（无类型校验）

- **风险等级**：高危
- **漏洞路径**：`app.py` 第 286～304 行（原始漏洞版本）

**漏洞描述**：
原始上传功能未对上传文件的类型进行任何检查。攻击者可以上传任意类型的文件，包括 PHP 脚本、Python 文件、HTML 页面、JavaScript 文件等。

```python
# 原始漏洞代码（无任何校验）
filename = os.path.basename(file.filename)
filepath = os.path.join(upload_dir, filename)
file.save(filepath)
```

**攻击场景**：
1. 攻击者登录系统后，访问 `/upload` 页面。
2. 选择一个 WebShell 脚本文件（如 `shell.php` 或 `cmd.jsp`）点击上传。
3. 如果服务器配置了解析 `static/uploads/` 目录下的脚本（如 Apache 的 `AddType` 或 Nginx 配置失误），攻击者可通过浏览器访问 `http://127.0.0.1:5000/static/uploads/shell.php` 执行恶意代码，获取服务器控制权。

**修复方案**：
1. 白名单校验文件扩展名，仅允许图片格式。
2. 校验文件内容（魔数签名），确保文件真实为图片。

**修复代码位置**：`app.py` 第 299～325 行。

**修复后代码**：
```python
# 扩展名白名单
allowed_extensions = {".jpg", ".jpeg", ".png", ".gif", ".webp", ".bmp", ".ico"}
original_ext = os.path.splitext(file.filename)[1].lower()
if original_ext not in allowed_extensions:
    return render_template("upload.html", error="仅允许上传图片文件"), 400

# 魔数校验
magic_bytes = file.read(12)
is_valid_image = (
    magic_bytes[:8] == b"\x89PNG\r\n\x1a\n"        # PNG
    or magic_bytes[:2] == b"\xff\xd8"                # JPEG
    or magic_bytes[:6] in (b"GIF87a", b"GIF89a")    # GIF
    or (magic_bytes[:4] == b"RIFF" and magic_bytes[8:12] == b"WEBP")  # WebP
    or magic_bytes[:2] == b"BM"                      # BMP
    or magic_bytes[:4] == b"\x00\x00\x01\x00"        # ICO
)
```

**复测结果**：
- 上传 `.txt` 文件 → 返回 400，提示"仅允许上传图片文件"
- 上传 `.php` 文件 → 返回 400，提示"仅允许上传图片文件"
- 上传 `.html` 文件 → 返回 400，提示"仅允许上传图片文件"
- 上传真实 PNG 图片 → 成功，显示预览
- 将非图片文件重命名为 `.png` → 魔数校验失败，返回 400

### V-02 文件名不处理（存储型 XSS 入口）

- **风险等级**：高危
- **漏洞路径**：`app.py` 第 304～309 行（原始漏洞版本），`templates/upload.html` 第 36～41 行

**漏洞描述**：
原始版本使用用户上传的原始文件名保存，未做任何净化处理。攻击者可通过上传一个包含恶意 HTML/JS 代码的 `.html` 文件，然后将其 URL 分享给其他用户，实现存储型 XSS 攻击。

```python
# 原始漏洞代码（使用用户原始文件名，无净化）
filename = os.path.basename(file.filename)
filepath = os.path.join(upload_dir, filename)
file.save(filepath)
file_url = url_for("static", filename=f"uploads/{filename}")
```

**攻击场景**：
1. 攻击者构造一个包含恶意 JavaScript 的 HTML 文件（如窃取 Cookie 的代码）。
2. 由于原始版本无类型校验，该 HTML 文件上传成功，保存在 `/static/uploads/malicious.html`。
3. 攻击者将 `http://127.0.0.1:5000/static/uploads/malicious.html` 链接分享给其他用户。
4. 其他用户在浏览器中打开该链接，恶意 JS 在同一来源下执行，可读取当前网站的 Cookie、LocalStorage 等敏感数据。
5. 即使 CSP 设置了 `script-src 'self'`，由于该 HTML 文件来自 `'self'` 范围，恶意脚本仍可执行。

**修复方案**：
使用 `secrets.token_hex(16)` 生成随机 UUID 作为文件名，彻底消除文件名相关的 XSS 风险。同时保留原文件的扩展名用于类型识别。

**修复代码位置**：`app.py` 第 327～331 行。

**修复后代码**：
```python
safe_filename = secrets.token_hex(16) + original_ext
filepath = os.path.join(upload_dir, safe_filename)
file.save(filepath)
file_url = url_for("static", filename=f"uploads/{safe_filename}")
```

**复测结果**：
- 上传文件 `test.png` → 保存为 `a1b2c3d4...snip...png`（UUID 格式）
- 上传文件 `../../../etc/passwd` → 路径穿越被 `os.path.basename()` 和 UUID 重命名双重消除
- 上传文件 `malicious.html` → 扩展名校验拒绝（不在白名单内）
- 上传文件名含中文 → 正常处理

### V-03 文件覆盖风险

- **风险等级**：中危
- **漏洞路径**：`app.py` 第 306～309 行（原始漏洞版本）

**漏洞描述**：
原始版本使用用户上传的原始文件名保存，且未检查文件是否已存在。同一文件名被不同用户上传时，后上传的文件会静默覆盖前者，导致数据丢失。

**攻击场景**：
1. 用户 A 上传头像 `avatar.png`，保存为 `/static/uploads/avatar.png`。
2. 用户 B 知道或猜测到文件名，也上传同名文件 `avatar.png`。
3. 用户 B 的文件覆盖用户 A 的文件，用户 A 的头像变为用户 B 的图片。
4. 如果覆盖的是关键配置文件或脚本文件（在无类型校验的情况下），可能导致更严重的后果。

**修复方案**：
使用 UUID 重命名，每个文件获得唯一名称，从根本上消除覆盖可能。

**修复代码位置**：`app.py` 第 327～331 行。

**修复后代码**：
```python
safe_filename = secrets.token_hex(16) + original_ext
```

**复测结果**：
- 两次上传同名文件 `avatar.png` → 保存为两个不同 UUID 文件，无覆盖

### V-04 CSP 保护缺口

- **风险等级**：中危
- **漏洞路径**：`app.py` 第 130～137 行（CSP 配置，原始漏洞版本）

**漏洞描述**：
原始 CSP 策略仅包含 `default-src 'self'` 和 `style-src 'self'`，缺少对图片加载源（`img-src`）、脚本（`script-src`）和插件（`object-src`）的明确限制。这使得：

1. 上传的 HTML 文件中的 `<script>` 标签会被 `'self'` 策略放行。
2. 上传的 SVG 文件（可含 JavaScript）也可能被加载和执行。
3. `<object>` 和 `<embed>` 标签可加载任意插件内容。

**修复方案**：
增强 CSP 策略，明确限制：
- `img-src 'self' data:` — 允许加载本域图片和 base64 内嵌图片
- `script-src 'self'` — 明确脚本只能来自本域
- `object-src 'none'` — 禁止所有插件加载（Flash、Java Applet 等）

**修复代码位置**：`app.py` 第 130～139 行。

**修复后代码**：
```python
response.headers["Content-Security-Policy"] = (
    "default-src 'self'; "
    "style-src 'self'; "
    "img-src 'self' data:; "
    "form-action 'self'; "
    "frame-ancestors 'none'; "
    "base-uri 'self'; "
    "script-src 'self'; "
    "object-src 'none'"
)
```

**复测结果**：
- 响应头包含 `Content-Security-Policy` 且包含 `img-src 'self' data:`
- 响应头包含 `script-src 'self'`
- 响应头包含 `object-src 'none'`

### V-05 文件上传大小限制修改

- **风险等级**：低危
- **漏洞路径**：`app.py` 第 23 行

**漏洞描述**：
`MAX_CONTENT_LENGTH` 从原来的 16KB（16384 bytes）修改为 16MB（16777216 bytes），扩大了 1024 倍。虽然图片上传需要更大的文件限制，但同时也扩大了大文件攻击的面。

**攻击场景**：
攻击者同时发起多个大文件（接近 16MB）上传请求，耗尽服务器磁盘空间或网络带宽，造成拒绝服务（DoS）。

**修复方案**：
保留 16MB 大小限制（图片上传的实际需要），增加 `os.makedirs` 确保上传目录存在。

**修复代码位置**：`app.py` 第 23 行。

**修复后代码**：
```python
MAX_CONTENT_LENGTH=16 * 1024 * 1024,  # 16MB
```

**复测结果**：
- 正常图片上传成功
- 当前未进行大文件压力测试

## 七、安全建议

1. **定期清理上传目录**：`static/uploads/` 中的文件不会自动删除，应建立定期清理机制。
2. **图片压缩与尺寸限制**：除文件大小外，可考虑对上传图片的像素尺寸进行限制，防止超大尺寸图片导致浏览器解析时性能问题。
3. **防盗链**：对于生产环境，可考虑添加防盗链机制，防止上传的图片被其他网站直接引用。
4. **日志审计**：记录所有文件上传操作（上传者、文件名、大小、时间），便于事后追溯。
5. **文件访问权限**：确保 `static/uploads/` 目录不允许脚本执行（如通过 Nginx 配置 `location /static/uploads/` 禁用 `fastcgi` 和 `uwsgi` 代理）。
