## 1. 实验目的

### 1.1 理解 CSRF 漏洞原理

CSRF（Cross-Site Request Forgery）是 OWASP Top 10 中的高危漏洞。其核心攻击原理：攻击者构造恶意网页，当已登录受害者访问时，恶意网页自动向目标站点发起请求，浏览器自动携带目标站点的 Session Cookie，服务器误认为是合法请求。

**CSRF 攻击三个前提条件：**

| 条件 | 说明 |
|:----:|------|
| Cookie 自动携带 | 浏览器向某域名发请求时自动附带该域名的所有 Cookie |
| 可预测的请求参数 | 攻击者能事先知道请求的所有参数 |
| 无 Token 验证 | 服务端不验证 CSRF Token，无法区分请求来源 |

### 1.2 理解 IDOR 漏洞

IDOR（Insecure Direct Object Reference）属于访问控制失败。当应用使用用户提供的输入直接访问数据对象，而未验证当前用户是否有权访问该对象时，即产生 IDOR 漏洞。

### 1.3 实验学习目标

- 理解 CSRF 漏洞的成因、攻击流程和防御方法
- 掌握 IDOR 水平越权的利用与修复（Session 绑定）
- 理解「不验证原密码」在密码修改业务中的安全风险
- 掌握 Burp Suite 代理拦截、参数篡改的完整流程
- 学习分层安全加固策略

## 4. 逐项漏洞分析与复现

### 4.1 V-01：CSRF 防护绕过（CWE-352）

**风险等级：** 🔴 严重（CVSS 8.8）

#### 漏洞代码

```python
@app.route("/change-password", methods=["POST"])
@csrf.exempt  # ❌ CSRF 豁免，不校验 Token
def change_password():
```

**分析：** 原始漏洞版本使用 `@csrf.exempt` 跳过了 CSRF 保护。攻击者可构造恶意页面，当已登录用户访问时自动发起 POST 请求修改密码。

#### 攻击流程

```
1. 攻击者在 evil.com 构造恶意表单：
   <form action="http://target:5000/change-password" method="POST">
     <input name="username" value="admin">
     <input name="new_password" value="hacked123">
   </form>
   <script>document.forms[0].submit();</script>

2. 受害者（已登录 admin）访问 evil.com
3. 表单自动提交 → 浏览器携带 session Cookie
4. Flask 收到请求 → @csrf.exempt 放行 → 密码被改
5. admin 密码变为 hacked123，攻击者获得控制权
```

---

### 4.2 V-02：IDOR 水平越权（CWE-639）

**风险等级：** 🔴 严重（CVSS 8.1）

#### 漏洞代码

```python
username = request.form.get("username", "").strip()  # ❌ 从表单获取
# ❌ 未检查 username 是否等于当前 session 用户
USERS[username]["password_hash"] = generate_password_hash(new_password)
```

**分析：** `username` 参数来自客户端表单而非服务端 Session，且未验证与当前登录用户是否一致。任何已登录用户可通过修改表单中的 `username` 值来修改任意他人的密码。

#### curl 验证

```bash
# alice 登录后，将 username 改为 admin
curl -b cookies.txt -X POST http://target:5000/change-password \
  -d 'username=admin&new_password=hacked123'
# ❌ admin 密码被 alice 修改成功
```

---

### 4.3 V-03：缺少原密码验证（CWE-306）

**风险等级：** 🔴 高危（CVSS 7.1）

#### 漏洞代码

```python
def change_password():
    # ❌ 完全没有验证原密码
    # 只要 session 中有登录状态即可修改
    USERS[username]["password_hash"] = generate_password_hash(new_password)
```

**分析：** 修改密码是最敏感的操作之一，必须验证用户知道当前密码。缺少原密码验证意味着：
- 如果用户离开电脑未锁屏，任何人可直接修改密码
- CSRF 攻击成功后，无需知道原密码即可篡改

---

### 4.4 V-04：密码强度校验缺失（CWE-521）

**风险等级：** 🟡 中危（CVSS 4.9）

```python
new_password = request.form.get("new_password", "")
# ❌ 无长度、复杂度校验，可设置 "1" 或 "123456"
```

---

### 4.5 V-05：用户名枚举（CWE-204）

**风险等级：** 🟡 中危（CVSS 5.3）

**分析：** 如果服务端对「用户不存在」和「密码错误」返回不同的错误消息，攻击者可通过枚举用户名来确认哪些用户注册过。修复方式：统一错误消息，无论用户名是否存在都返回相同信息。

---

### 4.6 V-06：双重表单一致性缺陷（CWE-684）

**风险等级：** 🟡 中危（CVSS 5.0）

**分析：** 表单中有 `new_password` 和 `confirm_password` 两个字段，但原始版本后端未校验两者是否一致。攻击者可通过 curl 直接提交不一致的值，导致用户密码被设置为意想不到的值，造成账户锁定。

---

### 4.7 V-07：新密码不能与原密码相同（CWE-521）

**风险等级：** 🟢 低危（CVSS 3.9）

**分析：** 修改密码时应检查新密码是否与原密码相同。如果相同，修改操作无意义但仍消耗服务器资源，且可能让用户误以为密码已变更（实为相同密码）。

## 5. 修复方案详解

### 5.1 CSRF 保护

```python
# 修复前：@csrf.exempt 跳过 CSRF 保护
@csrf.exempt
def change_password():

# 修复后：移除 @csrf.exempt，表单正常携带 csrf_token
def change_password():
```

同时前端表单添加 CSRF Token：
```html
<input type="hidden" name="csrf_token" value="{{ csrf_token() }}">
```

### 5.2 Session 绑定 — 只允许修改自己的密码

```python
current_user = session.get("username")
username = request.form.get("username", "").strip()

# 只允许修改当前登录用户自己的密码
if username != current_user:
    print(f"[安全警告] 用户={current_user} 试图修改用户={username} 的密码（已拒绝）")
    return redirect(url_for("profile", user_id=1))
```

### 5.3 原密码验证

```python
current_password = request.form.get("current_password", "")

# 验证原密码
user = USERS.get(username)
if user and not check_password_hash(user["password_hash"], current_password):
    print(f"[安全警告] 用户={username} 原密码验证失败")
    return redirect(url_for("profile", user_id=1))
```

### 5.4 密码强度校验

```python
if len(new_password) < 6:
    return redirect(url_for("profile", user_id=1))
```

### 5.5 统一错误消息（防用户名枚举）

所有验证失败都返回相同的位置（`redirect(url_for("profile", user_id=1))`），不区分具体失败原因，不暴露用户名是否存在。

### 5.6 确认密码一致性

```python
if new_password != confirm_password:
    return redirect(url_for("profile", user_id=1))
```

### 5.7 新密码不与原密码相同

```python
if new_password == current_password:
    return redirect(url_for("profile", user_id=1))
```

## 6. 修复前后代码对比

| 对比项 | ❌ 修复前（漏洞版本） | ✅ 修复后（安全版本） |
|--------|-------------------|--------------------|
| CSRF 保护 | `@csrf.exempt` 跳过 | 移除 `@csrf.exempt`，表单加 Token |
| 身份校验 | `username` 来自表单，可伪造 | 必须等于 `session["username"]` |
| 原密码验证 | 无 | `check_password_hash()` 校验 |
| 密码强度 | 无 | `len(new_password) >= 6` |
| 错误消息 | 可能暴露用户是否存在 | 统一跳转，不返回具体错误 |
| 确认密码 | 后端未校验 | 校验 `== confirm_password` |
| 新旧密码相同 | 无检查 | 拦截相同密码的修改 |

### 核心逻辑对比

**修复前（漏洞版本）：**
```python
@csrf.exempt
def change_password():
    username = request.form.get("username")           # 来自客户端，可伪造
    new_password = request.form.get("new_password")
    USERS[username]["password_hash"] = generate_password_hash(new_password)
    # ❌ 无 CSRF 保护，无身份验证，无原密码，无强度检查
```

**修复后（安全版本）：**
```python
def change_password():
    current_user = session.get("username")
    if username != current_user: return ...            # Session 绑定
    if not check_password_hash(user["password_hash"], current_password): return ...  # 原密码
    if new_password != confirm_password: return ...    # 一致性
    if len(new_password) < 6: return ...               # 强度
    if new_password == current_password: return ...    # 不与原密码相同
    USERS[username]["password_hash"] = generate_password_hash(new_password)
```

## 8. 安全编码规范总结

### 密码修改功能安全原则

| 原则 | 说明 |
|:----:|------|
| **CSRF 保护** | 所有涉及状态变更的 POST 请求必须带 CSRF Token |
| **Session 绑定** | 用户只能修改自己的密码，从 Session 获取当前用户 |
| **原密码验证** | 修改密码必须验证原密码是否正确 |
| **密码强度** | 密码必须有最小长度要求（≥6 位） |
| **一致性检查** | 两次输入的新密码必须一致 |
| **防枚举** | 错误消息统一，不暴露用户是否存在 |
| **审计日志** | 所有密码修改操作记录用户、IP、时间 |
